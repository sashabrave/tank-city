# Проверки и выпуск

## Политика тестов (с 03.10.2026)
Студийная практика, одобрена автором:
- **CORE** — около 30 быстрых тестов, ~1–2 минуты. Гоняется перед **каждой** сборкой и после каждого заметного изменения. Сборка только при зелёном CORE. Список — `tests/suites/core.txt`.
- **LONG** — боты и долгие прогоны, минуты на тест. Гоняется перед релизом (и после изменений баланса и боя). Список — `tests/suites/long.txt`.
- **Оконные, вручную** — замеры FPS, снимки и раскладки, которые headless не подтверждает. В наборы не входят, запускаются руками в окне.
- Всё устаревшее, дублирующее и нестабильное **удаляется**: архив — история git (`git log --diff-filter=D --name-only -- tests/`). Ценные проверки старых тестов перенесены в CORE (комментарии «from <старый тест>» в коде).
- Каждый тест обязан завершаться с ненулевым кодом при любой проваленной проверке. «Считает ошибки, но выходит с 0» — баг теста.

## Запуск
- `tools/run_tests.sh core` (или `quick`) — CORE.
- `tools/run_tests.sh long` — LONG.
- `tools/run_tests.sh full` — CORE + LONG.
- `tools/run_tests.sh имя1 имя2` — выбранные тесты по одному в папке проекта; тест с аргументами — в кавычках: `tools/run_tests.sh "balance_pacing 0 0 0 0 0 0 42 mid"`.

Наборы идут в `JOBS` потоков (по умолчанию 4, `JOBS=1` — по одному): каждый поток работает в своей мгновенной APFS-копии проекта (`cp -c`, ~2 с), потому что несколько Godot в одной папке дерутся за кэш `.godot` и дают ложные падения. У каждого запуска свой временный `HOME`: `user://` (профили, настройки) никогда не авторский. Итог — `tmp/test_runs/<время>/summary.txt` и лог на тест; код выхода 0 только при полностью зелёном прогоне.

Автозагрузка TestGuard (`scripts/test_guard.gd`) включается только для сцен из `tests/`: первая ошибка скрипта (сработавший `assert`, обращение к null) сразу завершает Godot с кодом 1 и строкой «TEST ABORTED»; зависший тест останавливается по `--test-timeout` (по умолчанию 180 с) с кодом 124.

Один тест вручную: `Godot --headless --path . tests/boot_profiles_revision.tscn`. Проверяй ошибки в выводе, а не только код завершения.

## LONG (`tests/suites/long.txt`)
- `playthrough` — бот проходит кампанию (ускоренное время); падает без победы над боссом или по тайм-ауту.
- `extreme_builds` — крайние сборки меты.
- `balance_v09` — сильная поздняя сборка проходит кампанию ботом playthrough, печатает строку BALANCE09; **падает** при тайм-ауте или 0 убийств (раньше выходил с 0).
- `balance_pacing 0 0 0 0 0 0 42 mid` — бот маршрута мира 1 для модели темпа (`tools/balance/run_pacing.sh` гоняет матрицу); падает при тайм-ауте или 0 убийств. Флаг движка `--fixed-fps 60` берётся из строки `## test-flags:` в .gd.
- `replay_v09` — повтор наград до этапа.
- `chaos_monkey` — случайные действия интерфейса и боя без ошибок.

## Оконные, вручную
Не входят в наборы; запуск `Godot --path . tests/<имя>.tscn` (без `--headless`). Снимки — в /tmp или в папку, указанную в тесте.
- Замеры: `perf_audit_visual` (FPS хаба, боя и карты; `--disable-vsync`, `-- --windowed`), `perf_ablation_visual` (цена каждой графической опции), `hub_performance`, `terrain_performance`, `shooting_performance`, `models_weather_stress`.
- Раскладки и картинка: `sandbox_admin_visual`, `run_result_visual`, `tablet_character_visual`, `command_screen_visual`, `typography_visual`, `graphics_styles_visual`, `fx_sun_visual`, `weather_visual`, `field_crates_visual`, `brick_shadow_visual`, `lights_v1_visual`, `route_look_visual`, `icon_kit_visual`, `icon_inspector_visual`.
- Эталонные кадры: `reference_shots_capture` (art_requests/reference_shots_v1/).

## Как добавить тест
1. Сначала найди CORE-тест той же системы и допиши проверку туда (функция или блок с комментарием). Новый файл — только для новой системы или сквозного сценария.
2. Шаблон: `tests/<имя>.tscn` (корневой узел со скриптом) + `tests/<имя>.gd`; в начале `Game.save_enabled=false; Settings.persistence_enabled=false; Game.sound_enabled=false`. Запись профиля — только в новый временный каталог (`Game.profiles.directory`, вместе с резервными копиями и индексом слотов), как в boot_profiles_revision и flow_full_loop.
3. Проверки — через `check(ok, msg)` со счётчиком и в конце `get_tree().quit(1 if failures else 0)` (или `assert`, который TestGuard превращает в код 1). Убедись, что провал даёт ненулевой код: временно добавь `check(false,"probe")`.
4. Не завязывайся на тайминги и нагрузку машины (бюджеты поиска пути, реальное время): такие тесты нестабильны в параллельном прогоне. Сид фиксируй; игровые случайности — только своими RNG.
5. Секунды — в `tests/suites/core.txt`; минуты — в `tests/suites/long.txt` плюс строка `## test-timeout: <секунды>` в .gd; только окно — суффикс `_visual` и раздел выше.
6. Удаляя тест, перенеси его ценную проверку в CORE и убери имя из наборов и этого гайда.

## Визуальная проверка
Оконный запуск обязателен для изменений компоновки, моделей и освещения. Проверь обе темы, русский и английский, длинные названия, узкий экран, кнопки закрытия и возврат управления. Headless использует фиктивный звуковой драйвер и не подтверждает слышимость.

## Экспорт
export_presets.cfg содержит macOS и iOS. Включай guides/*.md, data/locales/*.tsv и необходимые JSON; они не всегда автоматически попадают в экспорт как ресурсы. Проверяй содержимое экспортного пакета, а не только игру из редактора.
Перед экспортом запусти tools/build/stamp_build.sh: он записывает номер сборки (число коммитов ветки) в application/config/build. Номер видно в хабе рядом с FPS (scripts/ui/perf_overlay.gd, настройка show_fps) и в планшете → Об игре.

Локальная macOS-сборка не равна подписанному и нотарифицированному выпуску. iOS требует отдельного окружения, подписи и проверки на устройстве. Не публикуй сборки и не меняй подписи без отдельной задачи.

## Сборка macOS с запечёнными шейдерами (с 0.7.2)
В пресете macOS включён shader_baker: шейдеры компилируются при экспорте, и первый запуск новой сборки идёт около 8 с вместо 19 с. Запекание работает только при экспорте **в окне** (без `--headless`): `Godot --path . --export-release "macOS" build/macos/WarCats.app`. Экспорт в headless пропускает запекание.

## Замеры производительности
### Финальный замер (03.10.2026, MacBook M4, полный экран Retina 3420×2146)
`tests/perf_audit_visual.tscn` (окно, без vsync: `Godot --disable-vsync --path . tests/perf_audit_visual.tscn`, ключ `-- --windowed` — окно 1600×900) и `tests/perf_ablation_visual.tscn` (что стоит каждая графическая опция).
- FPS без ограничения: хаб 76–80, бой с толпой 73–77 (ночь 73), карта мира 86. Фризов (>33 мс) и рывков (>100 мс) нет; процессор ~5 мс на кадр, упираемся в видеокарту (~12 мс), 3D рисуется в ~2,4 Мп с FSR (авто-масштаб).
- Самое дорогое: размытие краёв (tilt-shift) −13% — облегчено до 8 выборок с мип-уровня 2 (тот же вид, +4%); SSAO −8%; ночью объёмный туман. Качество SSAO и размер тумана почти ничего не дают — оставлены.
- Холодный первый запуск (пустой кэш шейдеров): хаб готов за 7,7 с, самый долгий кадр 3,7 с — его прикрывает экран загрузки (scripts/ui/loading_screen.gd: держится, пока 8 кадров подряд не быстрее 40 мс). Повторный запуск — 1,6 с. Замер: `HOME=<копия профиля> ".../War Cats" -- --startup-hub`.

### Фризы при стрельбе (30.09.2026)
`tests/shooting_performance.tscn` (только оконный запуск): солдат стреляет в пустоту, в кирпич и во врагов; печатает медиану, p95, максимум и каждый кадр дольше 25 мс с разбивкой process / physics / render. Сохранения отключены.

Найденные причины: (1) компиляция шейдеров и первая загрузка моделей при первом появлении эффекта или врага — кадры 85–220 мс на первых выстрелах и 1–2,5 с при первом дроне/технике; (2) музыка — WAV общим объёмом 131 МБ загружалась синхронно и копировалась целиком (`duplicate`) при каждой смене трека; (3) варианты звуков эффектов грузились с диска при первом проигрывании.

Исправления: `scripts/effect_warmup.gd` один раз за сессию рисует под полом все виды снарядов, вспышек, осколков, обломков кирпича, монет, флага и все модели врагов и техники при загрузке первой комнаты; музыка грузится фоновым потоком (`music_controller.play_track` → `poll_pending`), без копирования ресурса; `audio_controller.warm()` при старте ставит все варианты эффектов в фоновую загрузку.

Результат на M4 после исправлений: первые выстрелы без всплесков, медиана 16,7 мс, p95 17–19 мс во всех сценариях. Редкие одиночные остановки ~1 с без нагрузки скриптов наблюдались только при параллельной работе другой тяжёлой сессии (Blender) и не воспроизвелись в чистом прогоне. Слабые устройства и iOS не измерены.

### Местность и хаб
`terrain_performance.tscn` запускается в оконном Godot: третий мир, комната 5, seed 14; измеряет создание комнаты, генерацию покрытий, отдельные вызовы поиска пути, затем кадры с видимым/скрытым лесом и шестью противниками. Сохранение игры и настроек отключено. Это локальный диагностический замер, а не универсальный FPS-бенчмарк: компиляция шейдеров, состояние окна и нагрузка ОС влияют на кадры.

На Apple M4 / Metal после оптимизации генерация покрытий заняла около 4 мс вместо 213 мс, создание комнаты — 84 вместо 472 мс. Вызовы поиска техники ограничены примерно 0,5 мс вместо синхронных 33–36 мс. В двух оконных замерах с шестью врагами медиана кадра составила 15,3–19,5 мс, p95 — 16,8–24,3 мс. Повторное использование готового маршрута заняло в среднем 0,0043 мс (100 вызовов). Лес, ветер и частицы оставались включены. Слабые устройства и iOS этим не проверены.

- `hub_performance`: оконные замеры покоя, приближения к штабу, меню строительства, движения и полностью построенного хаба ночью; отдельно измеряет `refresh` и обработку текста перед отрисовкой. На M4 повторное обновление закрытого хаба уменьшилось с 16,5–26,8 мс до 0,18–0,30 мс; число узлов до открытия каталогов — с 953 до 723. При движении со всеми постройками p95 кадра — 17,3 мс; ночью максимум выборки — 19,0 мс. В покое и около штаба кадры остались примерно 17–18 мс: оптимизация устраняет лишнюю сборку при обновлениях, а не меняет качество графики.
Первое открытие строительства в последнем запуске заняло 43 мс; устранение повторной сборки не означает отсутствие всех задержек первого открытия.
